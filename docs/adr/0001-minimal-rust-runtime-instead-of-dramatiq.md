# ADR: минимальный Rust runtime вместо Dramatiq

- Статус: предложено
- Дата решения: 9 ноября 2026
- Дата ревизии: 10 ноября 2026
- Область: доставка и исполнение Python async-задач
- Заменяет: Dramatiq broker, workers и task-адаптеры
- Не изменяет: Python Workflow, FSM, repositories, transactional outbox и собственную fan-out-механику

Ревизия сверяет решение с прототипом `agent-worker` и с исходниками закреплённых версий `apalis 1.0.0` и `apalis-redis 1.0.0`. Библиотека принята как транспорт прототипа. Она не считается доказательством гарантий переключения.

Эта ревизия дополнительно фиксирует очереди `default` и `quota`, повтор через новую постановку, лимит времени 30 минут и учёт метрик по исправленному Prometheus middleware, а не по stock-реализации Dramatiq.

## 1. Контекст

PostgreSQL остаётся источником истины для workflow. Переходы состояний, anti-overlap, продолжение pipeline и восстановление уже реализованы Python orchestration use cases. Rust к PostgreSQL не подключается, таблицы не создаёт и не знает `PipelineState` или `VALID_TRANSITIONS`.

Dramatiq удаляется целиком: broker, workers и task-адаптеры. На его место ставится свой Rust runtime, который исполняет уже существующие Python async-задачи. Python по-прежнему владеет workflow.

Runtime этого решения — текущий репозиторий. Бинарник называется `agent-worker`. Пока он совмещает несколько команд, запуск worker записывается как `agent-worker worker`. Имена зафиксированы в разделе соглашений и не смешиваются.

Жёсткие границы, которые эта ревизия считает уже установленными:

- Целевой интерпретатор — CPython 3.12 со сборкой GIL. Free-threading и `python -m asyncio ps` к этому runtime не относятся: внешняя инспекция asyncio из документации 3.14/3.15 и task trees Austin 3.14+ здесь отсутствуют.
- Обычный вызов Python API через PyO3 0.30 на этой сборке входит в интерпретатор. Отдельный Rust-поток GIL не отменяет. `Python::attach` не является без-GIL-доступом.
- Список живых `asyncio.Task` без входа в интерпретатор для 3.12 не является найденным поддерживаемым API. Диагностика, которая обязана отвечать при заблокированном интерпретаторе, читает заранее записанный Rust-реестр. `asyncio.all_tasks` допустим только как диагностический снимок, когда цикл исполняет callback.
- Отмена task выполняется callback'ом на потоке цикла (`call_soon_threadsafe`). Она не останавливает native-код, который держит GIL. Потеря Redis lease тоже не останавливает старую coroutine.
- CPython инициализируется один раз в процессе child. Supervisor Python не инициализирует. Повторная инициализация в том же процессе и `fork` после `Py_Initialize` не используются: единица recycling — новый процесс.
- Очереди продукта — `default` и `quota`. Внутренняя fan-out-механика ими не заменяется. Consumers, barrier, `XAUTOCLAIM` и recovery последней не меняются.
- Повтор после исключения — новая постановка того же `message_id` с `run_after` до подтверждения текущей попытки. `apalis-redis 1.0.0` сам повторно планирует статус `Failed` и `Pending`, пока `attempt < 25`, и не читает `max_attempts`. Завершённая ошибка поэтому возвращается как `Killed`, а не как `Failed`. `max_retries=0` остаётся допустимым и означает, что такого повтора нет.
- Короткий TTL бизнес-lock не защищает исполнение до 80 минут. Lock продлевается отдельно от lease сообщения. Эти два механизма не владеют одним и тем же Redis-ключом.
- Обрыв Redis не превращается в неограниченный буфер внутри процесса. `enqueue` выполняет одну отправку и возвращает ошибку.
- 80 минут — допустимая длительность задачи. Возраст вызова сам по себе не означает зависание. Длительный прогон на 80 минут этой ревизией не выполнялся.
- Гарантия «внешний эффект произошёл ровно один раз» не заявляется.

## 2. Решение

Rust executable запускает child-процессы со встроенным CPython. Rust исполняет доставку и вызов задачи. Python выполняет handler, hooks и use cases.

Стороны остаются модулями одного крейта. Бизнес-типы `job`, `names` и `ping` не открывают Redis и не вызывают Python. Redis, lock и файлы метрик — серверная сторона, её вызывает бизнес-решение. Импортируемый модуль и бинарник `agent-worker` — пользовательская сторона: они зависят от библиотеки, библиотека от них не зависит. Отдельный крейт на каждую сторону только переименовал бы те же модули. Карта элементов — `docs/model.toml`.

```text
Rust supervisor          Python не инициализирован
    ├── child            CPython 3.12 инициализирован здесь
    │     ├── Apalis + Redis backend
    │     ├── поток asyncio
    │     └── Python controller → существующие UC
    └── child
          └── та же структура
```

Закреплённые компоненты прототипа:

| Компонент | Версия в прототипе | Роль |
| --- | --- | --- |
| Worker и concurrency | `apalis 1.0.0`, feature `task-context` | `WorkerBuilder`, `Monitor`, `ConcurrencyLimitLayer` |
| Redis transport | `apalis-redis 1.0.0`, feature `task-tracking` | очередь, heartbeat, inflight, повторная постановка orphan |
| Rust async | `tokio` | supervisor, heartbeat, продление lock |
| Embedded CPython | `pyo3 0.30.1` | модуль `simple_q_runtime` через `append_to_inittab` |
| Async-мост | `pyo3-async-runtimes 0.30.0` | `into_future_with_locals` и `future_into_py` |

Собственный broker не пишется. Apalis даёт worker/backend. Redis backend при heartbeat вызывает `reenqueue_orphaned`: inflight мёртвого worker возвращается в очередь. Таблица возможностей самого crate помечает trait `ResumeAbandoned` как неподдерживаемый. Фактический путь восстановления — побочный эффект heartbeat живого worker, а не отдельный admin API. Пока ни один worker очереди не делает heartbeat, inflight этой очереди остаётся на месте.

Feature `task-tracking` включается сознательно. Без неё `renew_leases` передаёт в Lua пустой список task id, и скрипт обновляет ноль lease. Защита от повторной выдачи при живом процессе — heartbeat worker в sorted set, а не поле `locked_at`.

### Последствия

- Появляется второй исполняемый контур: supervisor и child. Отдельный HTTP-процесс им не становится.
- Runtime уже умеет принять сообщение, вызвать Python coroutine, дождаться hook и подтвердить сообщение. Workflow, FSM и fan-out в него не входят.
- Замена Dramatiq блокируется пунктами раздела 19, даже если runtime собирается и прогоняет короткие задачи.
- Включение `task-tracking` связывает продление per-task lease с тем, что worker context действительно содержит текущие task id. Это ещё нужно подтвердить длинным прогоном, а не только чтением исходника.

## 3. Разделение ответственности

### Rust

- Отправка и получение сообщений.
- Исполнение только очередей, переданных при запуске.
- Ограничение concurrency.
- Техническое владение сообщением через backend.
- Вызов Python async-задачи.
- Rust-реестр исполнений, ping цикла, сигнал отмены.
- Drain, завершение и пересоздание child.
- Технические события в лог. Имена метрик Dramatiq Rust не изобретает.

### Python

- Контроллеры и регистрация задач.
- DI, mappers и вызовы use cases.
- Вычисление ключей защиты.
- `next` и `err`.
- Все переходы FSM и anti-overlap.
- Transactional outbox и publishers.
- Completion, mark failed и административная отмена.
- Все workflow recovery-задачи.
- Собственная fan-out-механика.

### Последствия

- Ошибка доставки не становится переходом pipeline. Потеря владения сообщением не переводит pipeline в failed.
- Бизнес-recovery остаётся задачей, которую кто-то отправляет через runtime. Scheduler не вызывает recovery UC напрямую.
- Дублирование отправки в одном переходе запрещено: владелец отправки один — существующий Python-код, `next` или publisher.

## 4. Python-интерфейс

Приложение `--app` — реестр обычных async-функций (`simple_q.Registry`). Имя, очередь, `max_retries`, лимит времени и backoff задаются при регистрации. Имя функции — label `actor_name`. Класс `Controller` и декоратор `@task` остаются локальной границей lock для уже существующего фасада. Это не API Apalis. `simple_q_runtime` класса контроллера не содержит.

Форма фасада:

```python
class CacheController(Controller):
    queue = "default"

    @task(
        entrypoint=True,
        lock_key="cache:discovery",
        lock_ttl=30,
        skip_on_lock=True,
        max_retries=0,
        next=None,
        err=None,
    )
    async def discovery(self, orchestration_use_case, trace_ctx: dict | None = None):
        ...


cache = CacheController()
app.include_controller(cache)
```

Вызовы:

```python
await cache.discovery(...)          # локально, только entrypoint=True
await cache.recover_stuck.send(...) # постановка в очередь контроллера или задачи
```

`next` и `err` обязательны в декораторе. Значение — имя метода того же контроллера либо `None`. Пропуск аргумента не означает «хука нет».

Прототип не содержит `app.include_controller`: приложением команды `--app` является сам экземпляр контроллера, сейчас `simple_q.app:app`. Аргументы сообщения — JSON-объект. DI-объекты в сообщение не сериализуются; worker-side контроллер получает их заново.

`max_retries` — число дополнительных попыток после первой ошибки. Ноль допустим. Значение больше нуля не отвергается: повтор делает Python, постановкой с задержкой, до ack текущей попытки. Backend 1.0.0 по-прежнему нельзя просить об этом статусом `Failed`.

### Последствия

- Прямой вызов и `.send()` — разные сроки жизни. Локальный вызов идёт в том процессе, который его сделал, и пропадает вместе с ним.
- Ключи из примера `CacheController` не копируются на другие задачи. Их задаёт существующая семантика задачи.
- Сигнатуры hook: `(self, task_name, payload, result)` и `(self, task_name, payload, error)`. Имена параметров декоратора остаются `next` и `err`.

## 5. Защита вызова

Защита стоит на декорированной задаче.

```text
локальный вызов entrypoint ──┐
                              ├── одна граница → Python handler
вызов из worker ──────────────┘
```

Правила:

- Прямой вызов entrypoint проходит через тот же Redis lock, что и исполнение из очереди.
- Ключ вычисляет серверный Python-код. Клиент его не выбирает.
- В Redis ключ записывается как `lock:{lock_key}`. Значение декоратора префикс `lock:` не содержит. Пример: `cache:discovery` хранится как `lock:cache:discovery`.
- Один защищаемый вызов не исполняется конкурентно. Захват — `SET key owner NX PX`.
- `skip_on_lock=True` завершает дубликат без handler и без `err`. Сообщение при этом подтверждается: дубликат доставки не становится новым бизнес-запуском и не становится новым retry.
- Разные самостоятельные обработчики одного pipeline могут идти параллельно, потому что у них разные ключи.
- Lock продлевается примерно каждые `ttl/3`, пока reconcile считает Python-цикл отвечающим. Если цикл признан неотзывчивым, продление прекращается и ключ истекает.
- После `release` повторный последовательный запуск не блокируется этим ключом. Его запрещает существующий Python workflow.
- Task-level lock и inflight backend — разные ключи и разные протоколы. Один не обновляет ключи другого.

На прототипе проверено: второй `acquire` того же ключа получает отказ; локальный `execute` при занятом `demo:gate` возвращает `{"outcome": "skipped"}` и не входит в handler.

### Последствия

- Короткий `lock_ttl=30` безопасен для длинной задачи только вместе с продлением. Без продления ключ истечёт на работающем handler.
- Окно между `release` и ack сообщения существует. К этому моменту handler уже завершён, поэтому это повторный запуск, а не второй параллельный. Его держит workflow, не Redis.
- Ошибка самого `release` не меняет уже полученный результат handler или hook. Продление к этому моменту остановлено, а ключ истекает по TTL. Иначе успешная задача была бы записана как `Killed`.
- Общий модуль собирается как rlib для бинарника и как cdylib для колеса. Импорт не открывает Redis и не запускает Tokio. Соединение появляется в `configure(redis_url=...)`, после fork процесса, который будет отправлять.

## 6. HTTP

Через HTTP разрешено инициировать только dispatcher либо первую фазу workflow. Такие методы помечаются `entrypoint=True`. Универсального вызова стадии или handler по имени нет.

Существующие HTTP-интроспекция и административный cancel сохраняются. Cancel отправляет типизированную `mark_failed` задачу. Техническая отмена coroutine его не заменяет.

Локальный HTTP-вызов использует тот же lock, но исполняется в HTTP-процессе. Для работы, которая должна пережить этот процесс, используется `.send()`.

`apalis-board` остаётся диагностикой Redis-очереди. Он не заменяет существующую HTTP-интроспекцию. По умолчанию доска слушает `127.0.0.1:8080`. `BOARD_TOKEN` обязателен на любом адресе. `BOARD_INSECURE=1` снимает токен только у loopback. Worker перед исполнением вызывает `Job::validate` и отправляет неподходящее сообщение в dead-letter, не запуская актор.

### Последствия

- `await cache.discovery(...)` в HTTP легко принять за надёжную постановку. Надёжная постановка — только `.send()`.
- Non-entrypoint, вызванный как локальный метод, фасад отклоняет. Worker вызывает `execute` и это ограничение не обходит: очередь может исполнить любую зарегистрированную задачу.

## 7. Все операции проходят через задачи

В контроллерах явно регистрируются discovery / dispatcher, outbox publisher, рабочие стадии, completion, mark failed и recover stuck.

```text
APScheduler → task.send() → очередь → worker → Python task → существующий UC
```

Publisher тоже исполняется как задача. Его Python-логика читает pending events и отправляет следующие задачи через runtime. Внутренние батчи fan-out отдельными сообщениями runtime не считаются.

### Последствия

- Появляется обязательная регистрация задач, которые раньше могли вызываться напрямую из scheduler. Пропуск регистрации оставляет старый обходной путь.
- `.send()` сериализует только JSON-поля. Объект use case в очередь не кладётся.

## 8. Хуки next и err

Оба объявляются явно:

```python
@task(next="after_success", err="on_error")
```

либо явно отсутствуют: `next=None, err=None`.

Правила:

- `next` выполняется после успешного возврата handler и внутри той же coroutine.
- `err` выполняется при необработанном исключении handler. Исключение из `err` не вызывает `err` повторно.
- Hook не объявляет переход FSM.
- Если следующий шаг уже отправляет UC или outbox, `next=None`.
- Обработанный отрицательный результат UC не становится retry runtime.
- Падение процесса hook `err` не выполняет.
- В одном переходе один владелец отправки.

Прототип после `err` повторно поднимает исключение. Worker превращает его в транспортное завершение без retry, как описано в разделе 11. Успешный handler с `next` подтверждается как `Done`.

### Последствия

- Drain ждёт hooks, потому что они часть того же execution handle, а не отдельные сообщения.
- Ошибка в `next` идёт тем же путём, что и ошибка handler: один `err` для исходного исключения handler, без рекурсии, если упал сам `err`.

## 9. Очереди и отдельные машины

Минимальное разделение:

```text
default → обычные задачи, publishers, recovery
quota   → отдельные задачи квоты
```

Очередь задаётся при регистрации актора и может быть переопределена на задаче контроллера. Worker получает сообщения только из очередей запуска.

Имя очереди — непустое слово из строчных ASCII-букв и цифр. Дефис и подчёркивание отвергаются. `fan-out` остаётся названием существующей Python-механики и именем очереди не является. Суффиксы `.DQ` и `.XQ` в label метрики снимаются: в серии остаётся каноническое имя.

`batch_size` backend в прототипе равен 1, чтобы recycle не держал заранее запертую пачку неначатых сообщений.

### Последствия

- Неверное имя очереди — ошибка конфигурации на старте, а не молчаливое слияние с другой очередью.
- Ключи Apalis (`{queue}:scheduled`, `{queue}:active`, `{queue}:workers`, `{queue}:inflight:{worker}`, `{queue}:done`, `{queue}:dead`) принадлежат backend. Бизнес-lock туда не пишется.
- Машины отдельных задач запускаются со своим `--queues`, например `quota`. Это не подмена stream-групп существующей механики.

## 10. Минимальный reconcile

В child цикл lifecycle сопоставляет три независимых наблюдения:

```text
Rust-реестр execution handles
    ↔ ping потока asyncio
    ↔ продление бизнес-lock и heartbeat backend
```

Reconcile:

- пишет в реестр id, имя задачи, очередь, стадию `handler` и времена до входа в интерпретатор за списком task;
- считает цикл отвечающим, если `call_soon_threadsafe` исполнил callback в срок;
- не использует снимок `asyncio.all_tasks` для продления владения;
- прекращает продление бизнес-lock, просит отмену и завершает процесс кодом 2, когда ping не проходит дольше бюджета. Бюджет по умолчанию — лимит времени плюс 60 секунд, то есть 31 минута. Короткий синхронный участок в 60 секунд этот бюджет не исчерпывает. `SIMPLE_Q_PING_BUDGET_SECS` задаёт другой бюджет и минимум не поднимает;
- во время drain продолжает работать, пока процесс жив.

Ping, который не может войти в интерпретатор, не ставит следующий блокирующий вход, пока предыдущий не вернулся. Зависший native-кадр поэтому виден как неотзывчивость, а не как очередь из ожидающих `Python::attach`.

Отмена ищет task по имени, которое coroutine ставит себе на потоке цикла. Это сигнал, не подтверждение остановки и не `mark_failed`.

Reconcile не вызывает бизнес-recovery и не меняет pipeline.

Владение сообщением обновляет heartbeat Apalis, пока worker не переведён в `stop`. Бизнес-lock обновляет отдельный renewer. Общего ключа у них нет.

### Последствия

- Реестр показывает последнее известное Rust-состояние. Он не является списком всех приостановленных Python frames.
- Если GIL занят native-кодом на потоке цикла, ping истекает. Процесс должен умереть и освободить inflight по orphan-окну, а не ждать кадр.
- Код выхода 2 для supervisor — авария child, не плановый recycle. Supervisor поднимает новый процесс с паузой.

## 11. Длительное исполнение и ошибки

80 минут допустимы как длительность задачи, если её собственный лимит это позволяет. Lease сообщения не равен лимиту исполнения. Лимит по умолчанию — 30 минут (`1_800_000` мс), как прежний глобальный timeout Dramatiq. Истечение отменяет coroutine и считается неудачной попыткой: при оставшихся повторах сообщение ставится снова, на последней попытке вызывается `on_dead` с причиной `timeout`. Обычное исключение на последней попытке тоже вызывает `on_dead`, с причиной `retries`. Незарегистрированный актор вызывает `on_dead` с причиной `unknown_actor`. Сообщение, которое не проходит `Job::validate`, вызывает `on_dead` с причиной `invalid`. Poison решает Rust-функция `decide` после `INCR` и до `bridge::execute`: если счётчик доставок больше `max_deliveries`, сообщение хоронится, `on_dead` вызывается с причиной `poison`, и handler не стартует. Так зависший в native-коде или держащий GIL handler не получает следующую доставку. Повтор и timeout остаются в Python: им нужно исключение. Прямой `dispatch` и очередь в памяти по-прежнему хоронят poison сами, потому что до worker они не доходят. Хук получает `actor_name`, `kwargs`, `reason`, `message_id` и `retries`.

`Registry.on_send` вызывается в задаче отправителя до перехода в Rust и может дописать заголовки, видя `contextvars` вызывающего кода. `Registry.around_dispatch` оборачивает handler вместе с решением retry или dead; к началу хука уже доступен `current_message()`. Шаблон `lock_key` вида `cache:calc:{project_name}` остаётся в Python и раскрывается из kwargs в момент dispatch. После подстановки ключ состоит только из латинских букв, цифр и знаков `:._-` и не начинается с `lock:`. `simple_q.enable_memory` подменяет постановку очередью в памяти, а `drain` прогоняет её через `dispatch` до опустошения, включая сообщения, отправленные из handler.

Параметры heartbeat прототипа заданы явно, потому что `Default` у `apalis_redis::Config` ставит `missed_heartbeats = 10`, тогда как комментарий и serde-функция рядом задают 2:

- `heartbeat_interval` = 15 секунд
- `missed_heartbeats` = 4
- окно orphan = 60 секунд

Пока процесс heartbeating, возраст задачи сам по себе сообщение не отбирает. Если heartbeat прекратился, другой живой worker этой очереди может вернуть inflight примерно через окно orphan. Старая coroutine при этом может ещё работать.

Завершённая ошибка, когда повторов больше нет, возвращается как `AbortError`. Lifecycle Apalis записывает этому результату статус `Killed`. Lua 1.0.0 отправляет `Killed` в `{queue}:dead` и не планирует retry. Статус `Failed` этот путь не использует: иначе backend повторил бы попытку, пока `attempt < 25`, игнорируя `max_retries`.

Пока `retries < max_retries`, пауза считается формулой Dramatiq 1.18 `compute_backoff`: аргумент — число уже сделанных повторов, до увеличения счётчика. При `min_backoff` 15 с и `max_backoff` не ниже 60 с первые три паузы попадают в полуинтервалы `[7.5, 15)`, `[15, 30)` и `[30, 60)` секунд. Новая постановка несёт тот же `message_id` и `retries + 1`. Счётчик `dramatiq_message_retries_total` увеличивается один раз, на канонической очереди, только у постановки с задержкой. Повторная выдача после ETA задержкой не является и счётчик не двигает.

Повторная доставка после падения процесса — другой путь. Сообщение остаётся inflight, ack не делается, и позже orphan-скрипт ставит его снова. Скрипт сам счётчик доставок не увеличивает. Его увеличивает старт попытки в worker. Ключ `delivery:{message_id}:{retries}` лежит вне keyspace Apalis. Значение по умолчанию — 5, переменная `SIMPLE_Q_MAX_DELIVERIES`.

`persist_results` остаётся `true`. В `apalis-core 1.0.0` этот флаг — признак ack. `false` пропускает `TaskEvent::Complete`, и сообщение остаётся inflight. Готовые записи чистит отдельный обход: успешные через `SIMPLE_Q_DONE_TTL_SECS` (по умолчанию 24 часа), dead через `SIMPLE_Q_DEAD_TTL_SECS` (по умолчанию 7 суток, как `dead_message_ttl` Dramatiq). Обход идёт пачками `SSCAN`/`HSCAN`. `vacuum` Apalis для этого не используется: он читает весь hash и не снимает множества `done` и `dead`.

Потеря владения не переводит pipeline в failed.

Короткий прогон прежней ревизии проверял один `err` и запись в dead без scheduled и без done. Повторы, timeout и poison этой ревизией покрыты контрактными тестами на сжатом времени, а не ожиданием 7.5–60 секунд, 30 минут или суток.

### Последствия

- В доске Apalis бизнес-ошибка прототипа выглядит как `Killed`, а не как `Failed`. Это временное транспортное отображение дефекта Lua, а не семантика административной отмены.
- `TaskBuilder::max_attempts(1)` выставляется для будущей версии backend и сейчас Lua не читается.
- Окно orphan в 60 секунд — выбор прототипа для быстрого возврата сообщения. Оно не выведено из 80 минут. Если heartbeat замолчит на живой длинной задаче, повторная выдача возможна раньше, чем задача закончится.
- Ровно один внешний эффект не обещается. Его продолжают проверять UC и FSM.

## 12. Пересоздание worker-процессов

Supervisor поднимает `--processes` child. Child после `--max-tasks-per-process` завершённых внешних задач делает так:

```text
порог достигнут
    → pause: новые сообщения не берутся, heartbeat ещё идёт
    → дождаться пустого Rust-реестра
    → stop и закрытие backend
    → exit 0
    → supervisor запускает новый процесс со свежим CPython
```

`pause` выбран вместо немедленного `stop`, потому что `CallAll` в `apalis-core 1.0.0` после `stop` ждёт in-flight и до `poll_close` не вызывает `backend.poll_ready`. На этом участке heartbeat backend сам не тикает. `pause` оставляет цикл poll и heartbeat.

Считаются внешние завершения runtime. Уже начатые задачи доезжают, поэтому при concurrency больше 1 число завершений может превысить порог. Внутренние батчи fan-out в счётчик не входят: их в этом runtime нет.

Плановый recycle не убивает ещё допустимую длинную задачу. Неотвечающий цикл — отдельная ветка: процесс завершается кодом 2, сообщение остаётся для повторной доставки.

На прототипе проверено: два сообщения и `--max-tasks-per-process 1` дают два child с разными pid и exit 0 между ними. Третий child ждёт новую работу.

### Последствия

- Память и состояние интерпретатора сбрасываются только границей процесса.
- `SIGTERM` обрабатывает supervisor. Child на `SIGTERM` не заканчивает recycle: внутренний сигнал drain — `SIGUSR1` от supervisor. Иначе групповой `SIGTERM` нельзя отличить от планового exit 0.
- Grace period оркестратора должен покрывать самый длинный уже идущий handler. Короткий stop оборвёт то, что ADR считает допустимой длинной задачей.
- Аварийный child не вызывает `Py_Finalize` как условие корректности. Код 2 завершает процесс, чтобы не зависнуть в финализаторах.

## 13. Запуск

```bash
agent-worker worker \
  --app simple_q.app:app \
  --queues default \
  --processes 2 \
  --concurrency 1 \
  --max-tasks-per-process 500
```

```bash
agent-worker worker \
  --app simple_q.app:app \
  --queues quota \
  --processes 2 \
  --concurrency 1 \
  --max-tasks-per-process 24
```

`--child` скрыт и предназначен supervisor'у. Формат `--app` — `module:attribute`. Несколько очередей задаются через запятую: `--queues default,quota`. `--concurrency` по умолчанию равен 1. Числа процессов в примерах иллюстративные. `REDIS_URL` и параметры lock задаются окружением и регистрацией, не флагами бизнес-логики. Supervisor также поднимает `agent-worker metrics`.

Concurrency — число одновременно висящих Python-задач на одном asyncio-цикле процесса. GIL не даёт такого же числа параллельных исполнений bytecode. Параллельность полезна на `await` IO.

### Последствия

- Команда без подкоманды `worker` в этом репозитории не запускает пул: у бинарника есть ещё `execute`, `enqueue`, `admin` и `stubs`.
- `enqueue` в прототипе — прямой вызов той же функции постановки. Это не HTTP и не entrypoint.
- Ёмкость `--concurrency 12` нельзя планировать как 12 ядер Python.

## 14. Метрики

Имена, тексты HELP, labels `queue_name` и `actor_name` и корзины гистограммы совпадают с Dramatiq 1.18. Учёт совпадает с исправленным middleware, а не со stock `prometheus.py`:

- `queue_name` всегда канонический. Серии `.DQ` и `.XQ` не создаются.
- `dramatiq_messages_total` растёт на каждую завершённую попытку, включая исключение и skip.
- `dramatiq_message_errors_total` растёт, когда попытка закончилась исключением, в том числе timeout. Skip и poison сюда не входят.
- `dramatiq_message_retries_total` растёт один раз, когда повтор ставится с задержкой.
- `dramatiq_message_rejects_total` растёт на dead-letter: последнее исключение, последний timeout и poison.
- `dramatiq_messages_inprogress` и `dramatiq_delayed_messages_inprogress` — gauge `livesum`. Обработка отложенный gauge не трогает. Отложенный gauge считает только сообщение, которое этот процесс держит в памяти, и тем же `message_id` второй раз не растёт. Повтор в Redis через `run_after` в памяти процесса не лежит и gauge не двигает.
- Корзины `dramatiq_message_duration_milliseconds`: 5, 10, 25, 50, 75, 100, 250, 500, 750, 1000, 2500, 5000, 7500, 10000, 30000, 60000, 600000, 900000, +Inf.

Каталог задаётся `DRAMATIQ_PROM_DB`, `dramatiq_prom_db`, `PROMETHEUS_MULTIPROC_DIR` или `prometheus_multiproc_dir`. Адрес — `DRAMATIQ_PROM_HOST` / `dramatiq_prom_host` и `DRAMATIQ_PROM_PORT` / `dramatiq_prom_port`, по умолчанию `0.0.0.0:9191`, любой путь. Родитель один раз удаляет `*.db`. Ребёнок пишет файлы под `SIMPLE_Q_SLOT`, а не под pid операционной системы, и до первой метрики записывает `slot_<slot>.pid`. Перед scrape живые gauge мёртвого владельца снимаются: `mark_process_dead` удаляет только `gauge_live*_*.db`. Счётчики остаются. Перед новым child supervisor удаляет `gauge_live*_<slot>.db`, поэтому тысяча перезапусков слота число файлов не растит.

Runtime не включает prometheus layer Apalis: тот слой создал бы другие имена. Технические события tracing содержат `message_id`, `actor_name`, `queue_name` и `retries`.

### Последствия

- Stock middleware Dramatiq здесь не воспроизводится: он считал повтор дважды и держал отложенный gauge в режиме `all` с разными именами очереди на росте и на спаде.
- Статус backend `Done` / `Killed` нельзя напрямую копировать в старую метрику успеха: `Killed` означает завершённую ошибку без дальнейшего повтора.

### OpenTelemetry

У Rust-runtime нет своего OTLP-клиента. Child при импорте приложения забирает объект `Tracing` и отдаёт завершённые span'ы его Python-экспортёру. Экспорт идёт с отдельного потока операционной системы: потоки Tokio не вызывают `Python::attach` ради экспорта. Очередь ограничена `max_queue_size`. Если интерпретатор держит GIL и очередь полна, span отбрасывается, память процесса не растёт. `Resource` захватывается один раз на старте и прикладывается к каждому span, а не собирается заново. Ссылки span копируются. Заголовок `tracelink`, если это W3C traceparent, становится ссылкой process-span. В копию сообщения для Python dispatch записывается traceparent самого process-span. `job.headers` и повторная постановка сохраняют заголовки отправителя. `tracing=None` слой OpenTelemetry не создаёт и в Python для экспорта не ходит. `RUST_LOG` фильтрует только текстовый слой.

Код 2, в том числе неотзывчивый интерпретатор, буфер не сбрасывает: span'ы застрявшей задачи теряются, потому что GIL может быть занят. `Py_Finalize` не вызывается, на `atexit` полагаться нельзя. `force_flush` и любой другой flush экспортёра остаются в `on_stop` приложения. При обычном выходе child сначала вызывает `shutdown` провайдера Rust, и только потом `on_stop`.

Код 3 — неверная конфигурация трассировки: у экспортёра нет вызываемых `export` и `shutdown`, `resource` не является OpenTelemetry `Resource`, уровень target не разбирается, либо список targets пуст. Пустой фильтр отбрасывает все span'ы, поэтому это ошибка конфигурации, а не тихий режим. Если `targets` не передан, остаются `agent_worker=info`, `simple_q_runtime=info` и `apalis=debug`. Child завершается до старта worker, очередь не трогается. Для supervisor код 3 фатален: слот не засыпает и не перезапускается, supervisor останавливается с ошибкой. Любой другой ненулевой код по-прежнему ждёт паузу и поднимает процесс снова.

Производственное окно orphan остаётся 60 секунд. CI сжимает его (`SIMPLE_Q_HEARTBEAT_SECS=5`, `SIMPLE_Q_MISSED_HEARTBEATS=2`), в том числе для задачи, которая держит GIL чистым Python-циклом дольше этого окна. Окно в 120 секунд в CI не добавляется.

## 15. Объём первой реализации

Прототип закрывает транспортный срез:

```text
Rust
├── main.rs            # команды; supervisor не инициализирует Python
├── supervisor.rs      # процессы, SIGTERM, перезапуск
├── child.rs           # CPython, ping, drain, код 2
├── worker.rs          # Apalis + Redis; poison до входа в Python
├── bridge.rs          # execute, реестр, ping, cancel
crates/simple-q-runtime   # сообщение, очередь, lock, постановка; rlib и cdylib
crates/agent-worker       # supervisor, child, bridge, доска, scrape

Python
├── simple_q/registry.py     # регистрация акторов, повтор, timeout, шаблон lock_key
├── simple_q/metrics.py      # семь метрик Dramatiq
├── simple_q/controller.py   # локальный @task и lock
└── simple_q/app.py          # демонстрационный реестр
```

В первую продуктовую версию по-прежнему не входят:

- PostgreSQL из Rust;
- собственный Redis broker;
- новая FSM или workflow engine;
- новый бизнес-recovery;
- изменения внутреннего fan-out;
- приоритеты и дополнительные режимы;
- новый административный UI;
- проверенный 80-минутный прогон;
- замена имён метрик.

### Последствия

- Runtime можно собрать и прогнать на коротких задачах. Это не разрешение выключать Dramatiq.
- Демонстрационные задачи `demo`, `gated` и `boom` не задают ключи боевым контроллерам.

## 16. Критерии готовности

| Критерий | Состояние на ревизии |
| --- | --- |
| HTTP и worker не исполняют один защищённый вызов одновременно | Lock общий. Колесо `simple_q_runtime` импортируется отдельным процессом после `configure` |
| Независимые задачи одного pipeline работают параллельно | Обеспечивается разными `lock_key`; pipeline в этом runtime нет |
| Очереди исполняются только назначенными пулами | Worker подписан на очереди запуска. Имена продукта — `default` и `quota` |
| Длительная coroutine сохраняет актуальное владение | Механизм heartbeat и renew есть. Прогон 80 минут не делался |
| Неотвечающий Python loop обнаруживается reconcile | Ping и код 2 реализованы. Сценарий захвата GIL native-кодом не прогонялся |
| Падение child не оставляет назначение навсегда потерянным | Inflight возвращает heartbeat другого или нового worker. При нуле worker очередь стоит |
| Recovery и publishers запускаются через зарегистрированные задачи | Контракт принят. Таких задач в этом runtime нет |
| Recycling дожидается активных задач и заменяет процесс | Проверено на коротких задачах: pause, stop, новый pid |
| Разрыв Redis не копит запросы в процессе | `enqueue` на недоступный адрес завершается ошибкой, локальной очереди нет |
| Rust не выполняет переходы FSM и не перепроектирует fan-out | Соблюдено: этих подсистем в runtime нет |

Замена Dramatiq выполняется только когда строки этой таблицы закрыты, а не когда закрыт короткий прогон.

### Последствия

- Частично закрытый критерий нельзя отмечать как выполненный из-за похожего теста.
- Критерий «ровно один внешний эффект» в таблицу готовности не входит: решение его не обещает.

## 17. Ограничение выбора библиотек

Apalis и Redis backend — основа прототипа, не доказательство всех гарантий.

Перед переключением на закреплённых версиях ещё проверяются:

- общий lock настоящего HTTP-процесса и worker;
- владение на задаче длительностью порядка 80 минут, включая обновление `locked_at` при включённом `task-tracking`;
- реакция на цикл, заблокированный native-кодом с GIL;
- shutdown, при котором heartbeat не молчит дольше окна orphan;
- повторная доставка после убийства child и отличие этого пути от исключения handler;
- гонка закрытия Python loop при отмене в `pyo3-async-runtimes`.

Если версия не проходит критерий, перенос не выполняется. Обход через новую бизнес-логику в runtime запрещён. Текущий обход статусом `Killed` допустим только как временная транспортная мера прототипа и сам является блокером: продуктовый статус ошибки не должен зависеть от того, что Lua не читает `max_attempts`.

### Последствия

- Обновление Apalis — отдельное решение. Вместе с ним заново проверяются Lua heartbeat, orphan и handle results.
- Redis 8 указан в compose (`redis:8-alpine`). Короткий прогон этой ревизии шёл на Redis 7.0.15. Используемые команды (`SET NX PX`, sorted sets, hashes, lists, Lua) есть в обеих версиях; это не заменяет прогон на Redis 8.

## 18. Риски

Подтверждено чтением закреплённых исходников или прогоном прототипа:

1. `handle_results.lua` игнорирует `max_attempts` и повторяет `Failed`/`Pending` до 25 попыток. Любой путь, который вернёт `Failed`, нарушит `max_retries=0`.
2. `renew_leases.lua` не продлевает ни одного lease, если список task id пуст. Без `task-tracking` per-task `locked_at` застывает. От повторной выдачи тогда защищает только heartbeat процесса.
3. `Default` для `missed_heartbeats` расходится с собственным комментарием crate (10 против 2). Неявный default использовать нельзя.
4. После `stop` цикл worker не heartbeating, пока in-flight не опустеет. Длинный drain на `stop` короче окна orphan может быть выдан повторно.
5. Потеря lease и `task.cancel()` не останавливают coroutine в native-коде. Второй worker может начать ту же работу, пока первый ещё исполняется.
6. На CPython 3.12 снимок живых task без входа в интерпретатор недоступен как поддерживаемый API. Реестр может отставать от реальных frames.
7. Если `Python::attach` заблокирован, ping не должен запускать новые входы. Один застрявший blocking-поток остаётся до смерти процесса.
8. `pyo3-async-runtimes` публично описывает гонки отмены и закрытия цикла. Успешный путь прототипа дожидается future. Тайм-аут ping оставляет callback на цикле; это не управление задачей.
9. `simple_q_runtime` живёт в inittab бинарника. Отдельный HTTP-процесс эту границу lock/enqueue ещё не разделяет.
10. Имена метрик Dramatiq ещё не сверены с живым `/metrics`. Подключение prometheus layer Apalis создало бы параллельные имена.
11. Прогон 80 минут на производственном окне orphan не выполнялся. Сжатое окно прогоняется в CI на Redis 7 и Redis 8.
12. При нуле живых worker inflight не возвращается в очередь сам.
13. Concurrency ограничена одним asyncio-циклом и GIL. Планирование CPU по числу `--concurrency` будет неверным.
14. `err` не выполняется, если процесс умер до входа в hook.
15. Окно между снятием бизнес-lock и ack не является вечной дедупликацией. Повторный бизнес-запуск после этого окна должен держать workflow.

Не подтверждено и поэтому не считается свойством системы:

- ровно один внешний эффект;
- физическая остановка старой coroutine;
- автоматический переход pipeline в failed при потере владения;
- бесконечная Redis-дедупликация после истечения lock;
- что `Killed` останется правильным статусом после обновления Apalis.

## 19. Блокеры переключения

Пока выполнено хотя бы одно, Dramatiq не заменяется:

- Lua backend не отличает `max_retries=0` от повторной постановки `Failed`, и прототип всё ещё кодирует ошибку статусом `Killed`.
- Нет прогона на производственном окне orphan в 60 секунд и нет прогона на 80 минут. Интеграционный тест CI сжимает окно (`SIMPLE_Q_HEARTBEAT_SECS=5`, `SIMPLE_Q_MISSED_HEARTBEATS=2`) и на Redis 7 и Redis 8 проверяет, что задача длиннее этого окна не выдаётся второму child, а score worker и `locked_at` растут.
- Нет упаковки, в которой HTTP-процесс и worker вызывают один и тот же lock и один и тот же `enqueue`.
- Нет сверки `/metrics`: имена, labels, типы и значения.
- Не пройдены сценарии зависшего native-кода на производственном окне и закрытия цикла при отмене. Сжатый тест SIGKILL покрывает повторную выдачу: после окна счётчик доставок растёт, и при `SIMPLE_Q_MAX_DELIVERIES=1` Rust один раз вызывает `on_dead` с причиной `poison`, не входя в handler.

Расширение runtime бизнес-правилами, чтобы обойти любой из этих пунктов, решением не является.

### Последствия

- Статус ADR остаётся «предложено».
- Успешный `cargo test` и короткий сценарий worker этот статус не меняют.

## 20. Отказ от решений

| Отказ | Почему |
| --- | --- |
| Оставить Dramatiq | Замена broker, workers и адаптеров — сама цель. Отдельные классы Dramatiq не сохраняются «на время» |
| Написать свой Redis broker | Транспорт даёт Apalis. Свой протокол очереди дублировал бы backend и расходился с ним |
| Поставить Celery, RQ, arq, Taskiq или другой Python-broker | Нужен Rust-процесс, который исполняет существующие Python async-задачи, а не ещё один Python worker |
| Сделать Python хозяином процесса, а Rust — расширением внутри Dramatiq | Обратная упаковка. Worker-процесс принадлежит Rust, CPython встроен в child |
| Подключить Rust к PostgreSQL или перенести FSM | Источник истины и переходы остаются в Python. Иначе появляются два владельца pipeline |
| Заменить внутренний fan-out очередью runtime | Очередь доставляет handler. Stream, barrier, `XAUTOCLAIM` и recovery механики не являются этим handler |
| Считать idempotency key Apalis бизнес-lock | Ключ backend другой, а пустой ключ не дедуплицирует. Вечная дедупликация после release решением запрещена |
| Включить retry layer Apalis и отдавать `Failed` при `max_retries=0` | Lua 1.0.0 повторит такую ошибку до 25 раз |
| Считать 30 минут предельным возрастом задачи | 30 минут — лимит попытки по умолчанию. Lease и лимит — разные величины. Более длинный лимит законен |
| Реинициализировать CPython в том же процессе или форкать supervisor после `Py_Initialize` | Для extension modules это ненадёжно. Recycling равен новому процессу. Supervisor Python не поднимает |
| Считать `asyncio.all_tasks`, `python -m asyncio ps`, py-spy или Austin источником reconcile на 3.12 | Эти средства либо требуют интерпретатор, либо не дают поддерживаемый список task на 3.12, либо относятся к более новым версиям |
| Перейти на free-threaded CPython ради диагностики | Платформа зафиксирована как 3.12 с GIL |
| Отменять coroutine из Rust-потока минуя цикл | Мутация `Task` не с того потока не является управлением циклом |
| Считать технический `cancel` административным `mark_failed` | Cancel — сигнал циклу. Бизнес-отмена остаётся типизированной задачей |
| Дать HTTP универсальный вызов handler по имени | Разрешён только `entrypoint=True` |
| Буферизовать `.send()` в памяти при недоступном Redis | Обрыв Redis не должен копить работу внутри процесса |
| Продлевать бизнес-lock по устаревшему снимку task | Неотвечающий цикл прекращает продление |
| Держать два протокола владения одним ключом сообщения | Lease сообщения принадлежит backend. Бизнес-lock — отдельный ключ `lock:` |
| Включить prometheus middleware Apalis как продуктовые метрики | Имена разойдутся с текущим Dramatiq `/metrics` |
| Сделать `apalis-board` новым admin UI | Существующие интроспекция и cancel сохраняются. Доска — диагностика прототипа |
| Вызывать recovery UC из scheduler мимо задачи | Все операции этого контура идут через зарегистрированную задачу |
| Добавить в runtime новое бизнес-recovery или новую FSM, если библиотека не проходит критерий | Это обход блокера, а не исправление транспорта |

### Последствия

- Отказ действует, даже если отвергнутый путь короче в коде прототипа.
- Временный статус `Killed` не отменяет отказ от семантики «ошибка handler равна техническому kill» в продукте. Он только не даёт Lua сделать 25 повторов, пока блокер не снят.

## 21. Соглашения по именам

Имена ниже обязательны. Совпадения «почти то же» не используются.

### Репозиторий

| Что | Имя | Не использовать |
| --- | --- | --- |
| Бинарник | `agent-worker` | clap-имя `simple-q`, заголовок `simple-redis-q` |
| Подкоманда пула | `agent-worker worker` | голый `agent-worker` как синоним пула |
| Python-дистрибутив | `simple-q-runtime` | `simple-q`, имя очереди |
| Бинарный дистрибутив | `simple-q-worker` | имя очереди |
| Импортируемый пакет | `simple_q` | `simple-q` в `import` |
| Embedded-модуль | `simple_q_runtime` | `simple_q` |
| Приложение | `simple_q.app:app` | другой путь в `--app` примеров |
| Формат `--app` | `module:attribute` | пробел, `/`, точка вместо двоеточия |

### Очереди и Redis

| Что | Имя | Не использовать |
| --- | --- | --- |
| Очередь обычных задач | `default` | `simple-q`, `control`, `Default` |
| Очередь отдельных задач квоты | `quota` | `fanout`, `fan-out`, `fan_out` |
| Механика Python | fan-out | как имя очереди |
| Правило имени очереди | строчные ASCII-буквы и цифры, одно слово | дефис, подчёркивание, двоеточие, пустая строка |
| Бизнес-lock в декораторе | `cache:discovery`, общий вид `{контекст}:{действие}` | префикс `lock:` внутри значения декоратора |
| Ключ Redis для lock | `lock:{lock_key}` | ключи `{queue}:*` |
| Имя процесса Apalis | `agent-worker.{queue}.{hostname}.{pid}.{suffix}` | имя очереди с дефисом; один pid на все pod |

Ключ декоратора состоит из строчных сегментов, разделённых `:`. Пробелы запрещены. Сегменты берутся из уже существующей семантики задачи.

### Python

| Что | Форма |
| --- | --- |
| Класс | `CacheController`, суффикс `Controller` |
| Метод задачи | `snake_case`, глагол или устойчивое имя: `discovery`, `recover_stuck`, `process_stream` |
| Декоратор | `@task` |
| Параметры декоратора | `entrypoint`, `queue`, `lock_key`, `lock_ttl`, `skip_on_lock`, `max_retries`, `next`, `err` |
| Hook | строка с именем метода того же класса или `None` |
| Локальный вызов | `await controller.method(...)` |
| Постановка | `await controller.method.send(...)` |
| Поле трассировки | `trace_ctx` |
| Подключение контроллера | `app.include_controller(controller)` |

`next` и `err` — имена hook, не событий FSM и не методов Rust, которые надо вызывать отдельно от handler. В прототипе они исполняются внутри `execute`.

### Rust и сигналы

| Что | Имя |
| --- | --- |
| Модули | `supervisor`, `child`, `worker`, `bridge`, `lock`, `names` |
| Сообщение | `Job` версии 1: `message_id`, `actor_name`, `queue`, `kwargs`, `headers`, `retries` |
| Стадия реестра для всего вызова, включая hooks | `handler` |
| Плановый exit child | код 0 |
| Неотвечающий цикл | код 2; буфер span не сбрасывается |
| Неверная конфигурация трассировки | код 3; supervisor не перезапускает слот |
| Сигнал остановки supervisor | `SIGTERM` или `SIGINT` |
| Сигнал drain child | `SIGUSR1` |
| Признак child в окружении | `AGENT_WORKER_CHILD=1` |
| Адрес Redis | `REDIS_URL` |
| Адрес доски | `BOARD_ADDR`, по умолчанию `127.0.0.1:8080` |
| Токен доски | `BOARD_TOKEN` обязателен; `BOARD_INSECURE=1` только для loopback |

### Метрики

Имена остаются именами Dramatiq. Префикс не заменяется на `apalis_` или `simple_q_`. Labels — `queue_name` и `actor_name`. `queue_name` канонический.

### Последствия

- Путаница очереди runtime и механики fan-out — дефект конфигурации: очередь доставляет handler, а механика занимает другой протокол Redis.
- Дистрибутив на PyPI называется `simple-q-runtime`. Имя `simple-q` уже занято другим проектом. Импорт остаётся `simple_q`. Бинарник публикуется отдельным пакетом `simple-q-worker` той же версии. Как имя очереди, CLI и заголовка репозитория `simple-q` снято.

## 22. Что проверено этой ревизией

Короткий прогон прототипа на Redis 7.0.15:

- второй захват того же lock отвергается;
- локальный вызов при занятом lock возвращает skip и не входит в handler;
- локальный вызов при свободном lock входит в handler;
- `boom` из очереди один раз вызывает `err` и оказывается в dead, не в `scheduled` и не в `done`;
- пул одной очереди не забирает сообщение другой;
- имя `fan-out` отвергается;
- постановка в недоступный Redis завершается ошибкой;
- после одного завершённого сообщения child делает pause, stop и exit 0;
- supervisor заменяет процесс новым pid и на `SIGTERM` останавливает перезапуск.

Не прогонялось: 80 минут на производственном окне orphan, захват GIL native-кодом, отдельный HTTP-процесс, сверка `/metrics`. Задача длиннее сжатого окна orphan и SIGKILL child с повторной доставкой прогоняются в CI на Redis 7 и Redis 8.
